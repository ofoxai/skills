# Seedance 2.5 image-to-video: verified root cause (2026-08-29)

All claims below are independently verified by the main session via free `GET` polls against the real Ofox API on the actual job ids listed — not taken on trust from any single report.

## Root cause

`bytedance/seedance-2.5` + `frame_images` (image-to-video) requires the request to set `"aspect_ratio": "adaptive"` explicitly. This value is not in `ofox-video-core`'s current `VALID_ASPECT_RATIOS` whitelist (`16:9 9:16 1:1 4:3 3:4 3:2 2:3 21:9 9:21`), so:
- Passing any of the *documented* aspect ratios (or omitting it) with `frame_images` + `bytedance/seedance-2.5` fails — verified across 6 real attempts today with different combinations (some rejected client-side-equivalent 400 `invalid_request`, some `502 upstream_error`, none succeeded).
- Passing `"aspect_ratio": "adaptive"` + `frame_images` + `bytedance/seedance-2.5` succeeds. Verified job: `f3a2b2ab-d252-4567-809a-eb6f4dfe0ada` — polled independently, confirmed `status: completed`, `usage.video_cost: "0.9600000000"`, video downloaded via `ofox-video-core`'s own `poll` command to `test-output/f3a2b2ab-d252-4567-809a-eb6f4dfe0ada.mp4` (valid MP4, confirmed via `file`).

This is **not** a provider-routing issue (explicitly specifying `provider.type: "byteplus"` did not fix it — still failed with `aspect_ratio` values other than `adaptive`) and **not** a model-capability gap (Seedance 2.5's own model page confirms i2v support). It is specifically the `aspect_ratio` value.

`bytedance/seedance-2.0` does not have this requirement — the same `frame_images` shape with no `aspect_ratio` set at all succeeded on 2.0 on the first attempt (job `2fec25ea-91b0-44b9-a92a-6ca371c470d9`, $1.24, verified completed). Scope this fix to `bytedance/seedance-2.5` specifically; do not assume it generalizes to other models without separate verification.

## Secondary findings (verified)

1. **Reference image reliability**: a Wikimedia Commons direct-file URL (`upload.wikimedia.org/...`, 2400x1800, 2.9MB) was rejected by the upstream provider with a download-failure-shaped error on more than one attempt, despite being independently confirmed reachable via plain `curl` (200, valid `image/jpeg`) outside the Ofox request. A `picsum.photos` URL and a local-file-resized-then-base64-encoded data URI both worked. **Prefer base64 data URIs for `frame_images` when a local file is available** — more reliable than depending on the upstream provider being able to fetch an arbitrary third-party URL (likely bot/hotlink protection on some hosts, not something we control).
2. **Minimum reference image width**: the upstream error message (not just `error.code`) mentioned a specific minimum width around 300px in at least one rejected attempt. `ofox-video-core`'s current `print_api_error()` only prints the raw response body when `error.code` is *absent* — when a code like `invalid_request` **is** present, the specific `error.message` text (which had the actually-useful width detail) is currently swallowed and only the generic mapped explanation is shown. Fix: always show `error.message` alongside the mapped explanation, not only when the code is unrecognized.
3. **New error code**: `output_moderation_failed` — not previously documented in `.trellis/spec/skills/external-api-integration.md` or `ofox-video-core`'s error table. Verified job `c7bce29d-552b-4e73-8e7d-da083e7197ea`: `status: failed`, `error.code: "output_moderation_failed"`, message referenced audio-copyright concerns, and critically **`usage` is `null`/absent on this response — the job is not billed**. This happens *after* generation runs (a post-hoc content check on the generated output), not at job-creation time, so it cannot be caught by client-side validation — only documented as a possible terminal failure state with "not billed, retry with a different prompt" guidance (this is a genuinely new request each time, not a resubmission concern, since the original job already reached a terminal state).

## What needs to change in `ofox-video-core`

1. Add `adaptive` to `VALID_ASPECT_RATIOS`.
2. When `--frame-first-image`/`--frame-last-image` is set AND `--model` is (or defaults to) `bytedance/seedance-2.5`: force `aspect_ratio` to `adaptive` in the request regardless of what was passed (or left at default), and **print a visible one-line notice** explaining the override (never silently change a user-specified value without saying so — matches the `cloudflare-drop`/existing `ofox-video-core` "always report what was actually used" discipline already documented in `.trellis/spec/skills/index.md`). If the user explicitly passed a different `--aspect-ratio` alongside `--frame-first-image` for this model, still override it, but the notice must say what was requested vs. what was actually sent.
3. Support a local file path (in addition to the existing remote-URL support) for `--frame-first-image`/`--frame-last-image`: detect when the value is a local, readable file rather than an `http(s)://` URL, and base64-encode it into a `data:image/<ext>;base64,...` URI automatically (bash + existing `jq`/standard base64 tooling only — no new dependency). Keep the remote-URL path working as before for cases where a public URL is what the user already has.
4. `print_api_error()`: always print `error.message` from the response body (when present) alongside the mapped friendly explanation from `print_error_message()`, not only when `error.code` is absent. The mapped explanation stays (it's still useful framing), but the raw message must not be swallowed when it carries specifics like a minimum-dimension requirement.
5. Add `output_moderation_failed` to `print_error_message()`'s mapping: explain it happens post-generation (not at submission), is not billed, and the fix is to try a different prompt (new request, not a resubmission) — mirroring the existing terminal-failure guidance style for `failed`/`cancelled`/`expired`.
6. Bump `metadata.version` accordingly (this is at least two bug fixes bundled, prior pattern bumped once per PR/commit — use judgment, but document what changed in the version-adjacent prose either way).

## What needs to change in the scenario skills

- `seedance-product-video/SKILL.md` and `seedance-ad-creative/SKILL.md` both recommend `--frame-first-image` with the default model (`bytedance/seedance-2.5`) — both currently show example commands with an explicit `--aspect-ratio` value (e.g. `1:1`, `16:9`) that, per the root cause above, will be silently overridden to `adaptive` by the fixed script when combined with an image. Update both skills' examples/prose to reflect this (the aspect ratio they pick still matters for the *pure text-to-video* path in `seedance-ad-creative`, just not when an image is attached) and remove any implication that the shown `--aspect-ratio` value takes effect in the image-attached case.
- Both skills' "prefer a real photo" guidance should mention preferring a local file (auto-base64'd) over a remote URL when one is available, per the reliability finding above.
- Both skills' failure-mode tables should get the `output_moderation_failed` row.
